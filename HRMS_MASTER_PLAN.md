## 1. Overview

HRMS is **not a separate project** — it is an extension of the existing, live-production DPI Dashboard CRM (Next.js 16 + Supabase), built on the same codebase, same conventions, same RLS/RPC patterns already established throughout the app. It adds a fourth major surface (`/hr/*`) alongside the existing `/`(employee), `/admin/*`, and `/coordinator` sections.

**Two genuinely important, previously-established facts this plan depends on** (confirmed via direct DB/code research, not assumed):
- The old planning docs (`PROJECT_BIBLE_1.md`, `V2_MASTER_BLUEPRINT.md`, `V1_V2_COMPATIBILITY_MAP_1.md`) have **no detailed HR/Payroll spec**. They only contain: (a) the Geo-Fenced Attendance/Shift-Start system (built purely as a Lead-Distribution round-robin eligibility gate, **not** an HR feature), and (b) a dormant "HR" ticket-routing category placeholder for a future role. HRMS is fresh planning built on top of that thin foundation, not a continuation of a pre-existing detailed spec.
- **Two attendance concepts must never be conflated**:
  1. **Lead-Distribution Shift-Start window** (existing, relaxed, `lead_engine_settings` table) — gates round-robin lead eligibility only. **Never touched by HRMS work.**
  2. **HRMS Attendance strict on-time cutoff** (new, `hrms_settings` table) — independent calculation for HR reporting purposes, reusing the same raw `attendance.shift_start_at` data but applying its own stricter rule.

### 3.1 Attendance Module — ✅ Done

**Files**: `lib/calculateHrmsAttendanceStatus.ts`, `lib/exportAttendanceReport.ts`, `app/hr/layout.tsx`, `app/hr/attendance/page.tsx`. DB: `hrms_attendance_overrides` table, `mark_hrms_attendance_manual_atomic` RPC, plus two RLS fixes (`employees_select_hr`, `attendance_hr_select` — see "Post-launch bug fix" below).

**Post-launch bug fix (real-testing find)**: `role='hr'` was added to `employees.role`'s CHECK constraint, but nobody added a matching SELECT RLS policy for it on `employees` or `attendance` — an HR employee could see only their own row on both, via the pre-existing `*_select_own` policies (not the frontend query, which was already correct/unfiltered). Fixed with two new policies mirroring the existing `sales_coordinator`/`team_leader` broad-read shape. Verified live with both a positive test (HR sees all 14 active employees + all attendance rows) and a negative test (a plain employee still sees only themselves on both tables — confirms the fix didn't over-grant).

**Filters + export (added after initial build)**: Daily view became a **From–To date range** (defaults to today–today, so it behaves exactly like the original single-day view unless widened), rendered as a flattened Employee × Date table. Added an **Employee filter** (All / one specific) applying to both views. Added **PDF/Excel export on both views**, reusing the existing generic `lib/exportTable.ts` engine (`exportTableToPDF`/`exportTableToExcel` — same watermark, same branded header, zero new PDF logic), via a new thin wrapper `lib/exportAttendanceReport.ts` with two column shapes: a per-day detail export (Daily/Range view) and a per-employee aggregate export (Monthly Summary view) — mirrors `lib/exportLeadsReport.ts`'s exact "thin wrapper over the generic engine" pattern.

**Transparency pass (cutoff subtext + title fix)**: every Daily/Range row shows the exact shift-start time (already true since the filters piece, on both screen and export). Added a small subtext under the "Late Coming" badge — `Cutoff: 10:35 AM` (or the second-half cutoff, whichever applies to that row) — via the existing `formatTimeStringAsClock` helper from `lib/istTime.ts`, so no verbal explanation is ever needed for why a day was marked late. Export `reportTitle` corrected to `"DPI Attendance Report"` (was `"DPI HR Attendance Report"`/`"...Monthly Summary"`), matching `lib/exportLeadsReport.ts`'s `"DPI Lead Report"` naming convention exactly.

**Deliberately deferred**: `HALF_DAY` status only ever appears in the Monthly Summary view, never in Daily/Range, by design — it isn't a fact knowable from one day in isolation (it depends on whether that day was the 3rd+ late-coming day *that calendar month*, which requires whole-month context the Daily/Range view doesn't fetch). User explicitly confirmed this split (Daily/Range = raw per-day status, Monthly = policy-adjusted status) is fine as-is; making Daily/Range show the monthly-adjusted status is a real but bigger future enhancement (would need to fetch each visible employee's whole month, not just the selected range) — revisit only if actually requested.

**Symmetric on-time rule** (both halves have a "late coming" concept — corrected from an initial misunderstanding that only the first half did):
- First half: on-time ≤ **10:35 AM**, late-coming up to the existing (untouched) `first_half_start_window_end` = 11:30 AM.
- Second half: on-time ≤ **1:30 PM**, late-coming up to the existing (untouched) `second_half_start_window_end` = 2:40 PM.
- The calculation never needs to read those window-end values — the existing Start-Shift button is structurally incapable of producing a row outside them, so any recorded row is automatically within bounds.

**Monthly shared counter**: ONE combined late-coming allowance per employee per calendar month across *both* halves (not two separate counters). 1st and 2nd late-coming day in a month: free. 3rd onward: that day converts to `HALF_DAY`.

**Three-state day model**:
- `ON_TIME` — shift-started within cutoff.
- `LATE_COMING` — shift-started after cutoff but within the existing window (structurally guaranteed).
- `ABSENT` — **no `attendance` row exists at all for that date** (no absent-marking cron exists; a missed day simply produces zero rows).

**Manual override** (HR/Admin can mark Present/Absent for a day with no existing row — e.g. employee was physically present but forgot to click Start Shift):
- Zero schema changes to the existing `attendance` table.
- `PRESENT` inserts a real `attendance` row shaped exactly like a genuine shift-start (office's configured lat/lng + first-half start time from `lead_engine_settings`, `attendance_type='FULL_DAY'`) — so `calculateDailyHrmsStatus` needs no special-casing at all; it naturally computes `ON_TIME`.
- `ABSENT` touches nothing on `attendance` — the pre-existing "no row = ABSENT" rule already covers it.
- All traceability (who marked it, when, why) lives in the new `hrms_attendance_overrides` table, not on `attendance` itself. `UNIQUE(employee_id, date)` prevents double-marking. Reason is mandatory (matches every override-style RPC elsewhere in this app).
- Only reachable when no `attendance` row exists yet for that employee/date (enforced server-side in the RPC, not just UI-hidden).

**UI**: `/hr/attendance` — Daily view (per-employee status for a selected date, with the manual-override action appearing only when no row exists) and Monthly Summary view (per-employee counts of On Time / Late Coming / Half Day / Absent for a selected month, excluding the weekly-off day reused from `lead_engine_settings.sla_weekly_off_day`).

**Tested**: 9 pure-logic assertions (both cutoffs, the `HALF_DAY_FIRST` end-shift-correction edge case, absent handling, mixed-halves monthly rollup) all passed. RPC tested live in a rolled-back transaction (8 checks: duplicate-attendance rejection, duplicate-override rejection, unauthorized-caller rejection, RLS visibility for HR/Admin vs. a plain employee, and the stored row's exact shape) — all passed, zero residue confirmed on a fresh connection.

### 4.1 Document Management — ✅ Done (4/4 pieces)

- **HR uploads only** — no employee self-upload flow at all. HR can also *generate* documents (offer letters, experience letters) from templates.
- **Employee side is view-only, never download** — no download button/link/anchor for employees at all. Approach: never expose a real file URL to the employee's browser; a new `get_hr_document_view_path_atomic` RPC (SECURITY DEFINER, reuses `current_employee_id()`/`current_employee_role()`) authorizes the request, then a new API route (`app/api/hr-documents/view-url/route.ts`) — deliberately *not* copying this codebase's existing no-auth-check API-route convention, since this route gates private PII specifically — mints a 60s signed URL via the service role, only after the RPC confirms authorization. PDFs render as `<canvas>` via `pdf.js` core (new dependency), image documents via off-screen `Image` + `drawImage`; right-click/context-menu disabled; a watermark (employee name + "View Only" + timestamp) drawn onto the canvas itself. HR/Admin skip all of this — their bucket RLS already grants direct `createSignedUrl()` + real `<a download>`.
- **PDF generation + watermarking**: reuse `drawPdfWatermarkAndPageNumber` from `lib/exportTable.ts` (already proven, already in the bundle via lazy-loaded jsPDF) for every generated/downloaded document — zero new PDF logic.
- **Employee notified on new document upload** (approved add-on, folded into piece 2) — reuses the `notification` table, same loop-and-insert shape as everywhere else in this app.

**Schema (piece 1 — done)**: `hr_documents` (`employee_id, document_type` [CHECK: AADHAR/PAN/OFFER_LETTER/EXPERIENCE_LETTER/EDUCATIONAL/OTHER], `label, storage_path, file_mime_type, uploaded_by_employee_id, is_generated, created_at`; RLS: Admin all, HR all, Employee select-own-metadata-only) and `hr_document_templates` (`title, body, created_by_employee_id, created_at`; RLS: Admin + HR only, zero employee access) — both verified live.

**Piece 2 — done**: new RPC `register_hr_document_atomic` (admin/hr-gated, inserts the `hr_documents` row + notifies the employee `type='HR_DOCUMENT_UPLOADED'` in one call — exists specifically because `notification` has no HR insert grant, only `notification_insert_admin`, confirmed via direct query; a bare client insert would have failed for an HR caller). Tested live (rolled back): valid upload registers correctly with notification, invalid `document_type` rejected, unauthorized (plain employee) caller rejected, zero residue confirmed. New page `/hr/documents` (nav entry added to `app/hr/layout.tsx`): upload (file → private bucket directly via HR/Admin's own bucket RLS, then the RPC), employee filter, list with real Download (direct `createSignedUrl` + `<a download>`, HR/Admin only) and Delete (removes both the storage object and the metadata row).

**Piece 3 — done (the security-sensitive one)**: `get_hr_document_view_path_atomic` RPC (SECURITY DEFINER, admin/hr always allowed, else `employee_id = current_employee_id()`) — deliberately a separate authorization step from `hr_documents`' own SELECT policy, since RLS gates which *rows* you see, not which *columns* (the row's own `storage_path` would otherwise be visible to its own employee via a bare select). `app/api/hr-documents/view-url/route.ts` — deliberately breaks from this codebase's existing no-auth-check `app/api/*` convention (confirmed via direct check that `create-employee`/`delete-employee`/`data` routes verify nothing): the caller's own access token is forwarded to an anon-key client so the RPC's `auth.uid()` resolves as the real user, and only after that succeeds does a separate service-role client mint a 60s signed URL. `components/HrDocumentViewer.tsx` — canvas-only rendering (`pdf.js` core for PDFs, `Image`+`drawImage` for images — new `pdfjs-dist` dependency), watermark burned into the canvas pixels, right-click disabled, the signed URL never touches an `href`/`src`/`download` attribute or a console log anywhere (grepped to confirm). New employee-facing `/documents` tab, added to `EmployeeTabBar.tsx`'s both tab sets (same universal treatment Tickets already got).

**Tested**: RPC — 5 live checks (owner can view, **a different real employee is blocked**, admin/HR can view any, nonexistent doc rejected), zero residue. API route — 3 live HTTP checks (no auth → 401, garbage token → 403, missing documentId → 400), zero URL leaked in any failure case. Confirmed via grep: no `href=`/`.download`/`console.log` touches the signed URL anywhere in the employee-facing code.

**Post-launch bug fix (real-testing find)**: PDF viewing was broken end-to-end (`"getDocument - expected either data, range, or url parameter"`) — root cause confirmed precisely by reading `node_modules/pdfjs-dist`'s own source (`function getDocument(src = {})`): pdf.js v6 no longer auto-treats a bare string as the URL, it strictly reads `src.url`/`src.data`/`src.range` as object properties. The API route itself was already correct (verified separately) — the bug was purely `pdfjsLib.getDocument(body.url)` needing to be `pdfjsLib.getDocument({ url: body.url })`. Also fixed: document-type badge pills were `text-[10px]`, bumped to `text-xs` consistently on both `/hr/documents` and `/documents` list views (the upload form's type `<select>` was already `text-xs`, matching every other dropdown on that page, so left unchanged).

**Post-launch resilience fix (real-testing find)**: a stale document reference (deleted mid-testing) surfaced a raw `"document ... not found"` RPC error to the employee. Investigated live via direct DB query first — confirmed this was **not a code bug** (the referenced document genuinely no longer existed; `get_hr_document_view_path_atomic`'s query logic has no false-negative path). Added resilience anyway: `HrDocumentViewer` takes an `onNotFound?: () => void` prop, fires it when the API response's error string includes `"not found"`, and shows a friendly "This document is no longer available." message instead of the raw RPC error. `app/documents/page.tsx` wires `onNotFound` to refetch its list (document-loading logic refactored into a standalone `loadDocuments(employeeId)` so it's callable both on mount and from the callback) — the stale entry disappears on its own instead of lingering until a manual page reload.

**Piece 4 — done: Template Generation.** Confirmed before building: needed zero new tables and zero new RPCs. `hr_document_templates` already existed with `Admin+HR FOR ALL` RLS (plain client CRUD works, no wrapper RPC needed) and `register_hr_document_atomic` already had a `p_is_generated boolean DEFAULT false` parameter fully wired — the generate flow just calls the exact same RPC the upload flow does, with `p_is_generated: true`.

Both pieces live inside `app/hr/documents/page.tsx` itself (not a separate route — keeps Document Management as one page): (a) **Template management** — title + plain-text body with `{{placeholder}}` tokens, full CRUD. (b) **Generate flow** — pick Template + Employee + Document Type + Label; the template body is scanned for `{{...}}` tokens, auto-filling `employee_name`/`department`/`role`/`email`/`today_date` from the employee record (the only fields that actually exist on `employees` — confirmed via schema check there's no `position`/`salary`/`joining_date` column, so anything else becomes a required manual input generated dynamically per-template) and prompting for everything else. On Generate: substitute all tokens → render a PDF client-side → upload to the same private `hr-documents` bucket (same path convention as manual uploads) → `register_hr_document_atomic(..., p_is_generated: true)`. From there it's indistinguishable from an uploaded document — same list, same employee-facing view-only viewer.

**One deliberate deviation from this section's original wording**, decided with the user before implementing: the spec above says PDF generation reuses `drawPdfWatermarkAndPageNumber` — reconsidered and changed. New `lib/generateHrDocumentPdf.ts` (`buildHrDocumentBlob`) mirrors `buildCostSheetDoc`'s precedent instead (portrait, clean letterhead, plain page number, **no** diagonal watermark), for the exact reason that function's own comment already states: a Cost Sheet (like a generated offer/experience letter) is handed directly to an external party, not an internal report, and a repeated "CONFIDENTIAL" watermark would read as the wrong kind of document. Still reuses the jsPDF lazy-import idiom and the general "build a Blob, then upload it" pattern. `COMPANY_NAME` was exported from `exportTable.ts` (was a private const) so this new file can reuse it rather than duplicating the literal string.

All 4 pieces done — module complete.

### 4.1b Company SIM / Email Tracking — ✅ Done (4/4 pieces)

New sub-module, same "Document Management" family (Admin/HR asset tracking). Company issues employees a SIM card, which is how their company email gets created; Admin/HR need to track sim_number ↔ email_address ↔ email_password per employee, and be able to **transfer** a SIM/email to a new employee when someone leaves, with full history of who had it and when.

- **Dedicated tables, not a new `hr_documents` type** — this is structured, reassignable-with-history data, not a file; forcing it into `hr_documents` would mean either always-NULL columns or losing the reassignment-history model entirely.
- **Password storage: Supabase Vault**, reusing the *exact, already-proven, already-in-production* pattern from `meta_datasets`/`admin_create_meta_dataset`/`get_meta_dataset_credentials`/`admin_rotate_meta_dataset_token` (confirmed via direct source read, a real live secret already exists in `vault.secrets`) — `vault.create_secret(password, name, description)` returns a `uuid` stored in `company_sim_assignments.email_password_secret_id`; the plaintext is only ever readable via a new admin/hr-gated `get_sim_assignment_credentials_atomic` RPC joining `vault.decrypted_secrets`; rotation via `vault.update_secret`.
- **`company_sim_assignments`** (piece 1 — done): `sim_number, email_address, email_password_secret_id, created_by_employee_id, is_active, created_at, updated_at`. Deliberately **no `current_employee_id` column** — an earlier draft of this plan proposed one, corrected during planning: that would be a second source of truth alongside the history table, the exact class of bug this project's Golden Rule exists to prevent. "Who has it now" is always a query against the history table below, never a duplicated column.
- **`sim_assignment_history`** (piece 1 — done): mirrors `lead_history`'s exact shape (`sim_assignment_id, employee_id, assigned_at, unassigned_at` nullable, `assigned_by_employee_id, reason` nullable, `is_active`) — same idiom, not a new one. Unique partial index `sim_assignment_history_one_active` on `(sim_assignment_id) WHERE is_active` (mirrors `lead_history_one_active_assignment`) guarantees exactly one current holder at a time.
- **RLS on both**: Admin + HR only, zero employee access (administrative asset/credential data) — verified live.
- **Piece 2 — done**: `create_sim_assignment_atomic` + `get_sim_assignment_credentials_atomic`, both admin/hr-gated. Tested live (7/7 checks, rolled back): full Vault round-trip verified (password written then read back matches exactly), missing-field and unauthorized-caller rejections all correct, history row correct. Fresh-connection check confirmed zero residue — including `vault.secrets` itself, which is genuinely transactional and rolled back cleanly (a detail not previously verified in this project).
- **Piece 3 — done**: `transfer_sim_assignment_atomic` — mirrors `force_reassign_lead_atomic`'s exact shape. `p_new_employee_id` nullable (the "drawer" case). Tested live, 6/6 scenarios (rolled back, zero residue): normal transfer (old holder deactivated + `unassigned_at` set, new holder active), rejecting a transfer to the already-current holder, the drawer case (deactivate with no new row), rejecting a second drawer call with nothing to unassign, reassigning out of the drawer (correctly creates the one new active row with no stale ones), and unauthorized-caller rejection.
- **Piece 4 — done**: UI — new `/hr/sim-assignments` page (own nav entry in `app/hr/layout.tsx`, not a tab inside `/hr/documents`, per plan). Employee list + `company_sim_assignments`/`sim_assignment_history` (active holders only) loaded in parallel and merged client-side. Create form (sim number/email/password/employee/reason → `create_sim_assignment_atomic`). Per-row Transfer (employee picker with a blank "Unassign only" option for the drawer case, + reason → `transfer_sim_assignment_atomic`). Per-row Show/Hide password, fetched on-demand via `get_sim_assignment_credentials_atomic` (never preloaded for every row).

All 4 pieces done — module complete.

## 5. Key Architectural Principles (apply to every module above)

1. **Reuse existing tables/RLS/RPC patterns wherever possible.** Golden Rule, applied repeatedly: `attendance` reused for manual-present entries instead of a new table; `ticket_categories`' HR row reused instead of a new routing mechanism; `notification` reused for Announcements instead of a new display system; `leads.lead_type`'s discriminator-column shape reused for `expenses.expense_source`.
2. **The existing Lead-Distribution Shift-Start system is never touched by HRMS work.** Two genuinely independent attendance concepts, permanently. `lead_engine_settings` may be *read* (e.g., office coordinates, weekly-off day) but never modified by HRMS code.
3. **Admin always has universal access; HR's access is scoped** — matches the pattern already established everywhere else in this app (Admin is a superset role for tickets, leave, lead transfers, and now HRMS). Where HR's role in a specific module is explicitly read-only (Expenses), that's a deliberate exception stated per-module, not a general rule.
4. **`feature/hrms` branch only.** `main` and `dev` are never touched by this work unless the user explicitly says so. Every piece is implemented one at a time, diffs shown, user approves before the next piece starts.
5. **Test before calling anything done** — live RPC tests in rolled-back transactions (zero residue verified on a fresh connection afterward), plus pure-logic assertions for calculation modules — same rigor used throughout the rest of this codebase's session history, not lighter-touch just because it's a new module.
